## Findings

### R1 — A short agent task can start keeping your Mac awake after it has already finished

**What this could look like with the plugin installed:** you ask an agent a quick question. Before the plugin's ten-second waiting period ends, it temporarily loses the ability to read Herdr's agent list. The agent might finish normally, but the plugin still remembers it as working. At ten seconds, instead of waiting for fresh status, the plugin begins keeping the Mac awake. A coffee cup could appear if sidebar updates still work; if those updates also fail, the extra protection may have no visible cup.

**The stakes:** you walk away expecting an idle Mac to be free to sleep, but this agent's protection is active even though no work may remain. A later successful status read can correct that; if the uncertainty persists, the protection can last until the original eight-hour deadline. The deadline is not extended beyond that original limit. This can happen during a temporary failure to read Herdr, without you changing any settings or explicitly requesting protection.

**How could the read fail?** This is local communication with Herdr, not an internet connection; losing Wi-Fi is not the scenario. A request can time out (the plugin allows five seconds), return an API error, or end without a reply. There is also a concrete pane-lifecycle race: Herdr documents that subscription setup rejects the whole request if a referenced pane has disappeared. This plugin sets up subscriptions while refreshing its agent list, so a pane closing between listing and subscription setup can fail that refresh. A failed local host-verification or configuration read reaches the same error path, though those were not reproduced here. Confirmed server disappearance is a different, already-handled path that shuts protection down.

**Likelihood and severity:** we have not measured the frequency of these failures in normal use, and this review does not claim that the connection commonly breaks. The bug needs the failure to overlap the initial waiting period. It is a concrete error-handling defect in a path the plugin already supports, not a proposal to build a general reliability framework. The recommendation follows the agreed rule for uncertainty; a decision to accept the risk should acknowledge that its real-world frequency is unknown.

**What should happen:** do not begin automatic protection without fresh working evidence. If protection was already active before the outage, preserve its existing deadline instead. The distinction is starting new protection versus preserving protection already earned.

**Fix before merge.** References: `herdr/caffeinate/src/monitor.ts:174–183`, `:90–95`; `src/model.ts:125–128`; `docs/design.md:20,51`.

**Expectation:** uncertainty preserves existing deadlines but cannot create protection; an uncertain initial delay must await positive working evidence.

**Observed:** the outer refresh catch sets `gap`/`error`, retaining the previous `working` phase. It then calls `sync()`, whose tick promotes an elapsed pending lease. The per-agent observation catch correctly supplies uncertainty; the whole-refresh failure path does not.

**Reproduced:** observe idle, then working; fail listing; advance ten seconds; refresh. The monitor requests one new assertion with deadline `1800028800000`, while reporting `list unavailable`. Expected active count: zero. Host/config-read failures share the outer catch; only list failure was executed in this reproduction.

**Recommendation:** propagate whole-refresh uncertainty before automatic promotion, preserving valid leases and the original pending timestamps. Recover only the remaining original duration after positive working evidence returns. Add monitor-level outage-during-delay and recovery tests; existing coverage starts the outage after a manual lease already exists.

**Decision:** require this correction before merge. Confidence: reproduced through the actual built monitor/model with fake ports, not native assertion acceptance.

### R2 — After losing track of an agent, the plugin can give it a new automatic eight-hour allowance

**What this could look like with the plugin installed:** the plugin last saw an idle agent. Herdr's event connection then drops while the plugin is checking its status. When that check returns, the agent is working—but the plugin cannot reliably know when this work started or what happened during the interruption. Nevertheless, it can treat this as a newly observed start and automatically turn on caffeination after ten seconds.

**The stakes:** work whose start the plugin missed gets automatic protection it should not receive. Its eight-hour allowance is measured from the plugin's later observation rather than a reliably observed start, potentially keeping the Mac awake later than intended. Unlike R1, the agent may genuinely still be working; the problem is inventing a new automatic allowance after losing the information needed to justify it. A brief event-connection failure at the wrong moment is sufficient; the rest of Herdr need not stop working.

**How realistic is the connection interruption?** Herdr explicitly documents a case where it closes only the event subscription while other clients remain connected: a subscriber falls behind retained event history and receives `events_lost`. That can result from enough event activity relative to the subscriber's progress; history is shared across event types. The underlying Unix socket is not assumed to randomly lose bytes. This is an application-level gap reported by Herdr itself, with a specified reconnect/resync procedure. The available local Herdr source implements that path.

**Likelihood:** the triggering protocol condition is real, but we have not induced an actual history overrun or measured how often it occurs. R2 additionally needs the gap notification to arrive during an outstanding observation. Thus this is a reproducible timing defect at a documented recovery boundary, not evidence that everyday plugin use often fails. R1 does not require this particular event-gap mechanism; an ordinary whole-refresh failure is enough for R1.

**What should happen:** keep already-established deadlines, but do not invent a start for newly discovered ongoing work. You can explicitly caffeinate that work yourself, or automatic protection can wait for a reliably observed subsequent run.

**Fix before merge.** References: `herdr/caffeinate/src/monitor.ts:143–150`, `:188–191`; `src/main.ts:85–87`; `src/herdr.ts:287–297`; `src/model.ts:80–94`.

**Expectation:** subscription loss must invalidate authority to infer a new run from a stale idle baseline. Current state cannot reconstruct a missed start time.

**Observed:** `markGap()` queues the invalidation behind the entire active refresh. A pending observation can therefore commit working evidence against the old idle baseline before the gap is recorded. Later gap processing clears `boundaryKnown`, but leaves the newly manufactured pending lease.

**Reproduced:** establish idle; hold a working observation; call `markGap()`; release the observation; process the queued gap; advance ten seconds and refresh. A pending lease survives and becomes active. Expected active count: zero.

**Production reachability:** subscription failure calls `onUnavailable()` before `onInvalidate()`. `main.ts` queues `markGap()` without cancelling the active refresh. Observation requests use separate sockets, so subscription failure need not fail the outstanding observation. This transport reachability is code-path evidence; the executed reproduction uses fake ports.

**Recommendation:** record invalidation immediately and check its generation before committing authority to infer a run. Merely moving the existing Boolean assignment outside the queue is insufficient: the current check precedes an awaited observation. Preserve genuinely existing leases/pending deadlines; do not broadly discard valid entitlement. No generalized event framework is needed.

**Decision:** require an in-flight gap regression and correction before merge.

### R3 — Unplugging may leave the plugin keeping the Mac awake on battery

**What this could look like with the plugin installed:** an agent is caffeinated while your laptop is plugged in. You unplug it, expecting this AC-only plugin to stop preventing idle sleep. If the plugin is waiting on a slow Herdr status request, it does not get around to checking the battery until that unrelated request finishes. The next power check cannot get ahead of the stalled status work.

**The stakes:** the laptop can remain protected from idle sleep on battery longer than intended, potentially wasting battery if left unattended. This does not mean the plugin prevents lid-close sleep or overrides low-battery shutdown. The issue is delayed removal of its idle-sleep protection. Several sequential slow reads can make the delay longer than one request timeout.

**What does closing the lid do?** Normally, closing a MacBook's lid puts it to sleep; this plugin's `caffeinate -i` assertion does not override that. Supported closed-display/external-monitor configurations are an exception where macOS can keep a closed laptop running for reasons independent of this plugin. Do not rely on Caffeinate to keep agents running with the lid shut. The installed `caffeinate` manual distinguishes `-i` (prevent *idle* system sleep) from `-d` (prevent display sleep); we use `-i`, not display-wake flags. Physical lid/display behavior has not been tested in this review.

**What is actually waiting?** The plugin both listens for Herdr events and polls. Its ordinary refresh is ordered like this:

1. Verify the local Herdr host and read settings.
2. Request the agent list and then each agent's details, waiting for replies in sequence.
3. Read the power source and add/remove sleep assertions.
4. Update sidebar cups; after the whole refresh finishes, wait about one second before the next periodic refresh.

An event can request another refresh sooner, but it does not give power checks a separate execution path. If a status request is slow—for example, Herdr has not processed or answered it yet—step 2 awaits that reply or its five-second timeout. Step 3 has not run yet. Other refresh/tick requests queue behind this one. JavaScript's event loop need not be frozen: this is ordering imposed by our code, not a claim that the CPU is stuck. The suggested correction separates the safety cadence from this status-update queue.

**What should happen:** power changes should be checked on their own bounded cadence, targeting the agreed two-second response in normal operation, rather than waiting for all agent-status and sidebar work. We reproduced a fake assertion remaining active through a real 2.3-second wait; we have **not** measured physical unplug behavior on an installed plugin.

**Fix before merge.** References: `herdr/caffeinate/src/monitor.ts:90–116`, `:119–183`; `src/main.ts:48–68`; `src/herdr.ts:70–81,209–250`; `docs/design.md:119`.

**Expectation:** AC-only eligibility, with periodic unplug checks targeting at most two seconds in normal operation. This is not a hard-real-time guarantee.

**Observed:** power is read only after host/config/list/sequential-agent work. The next periodic cycle is scheduled after the refresh and token publication complete. `tick()` enters the same serialized refresh queue. Herdr requests have five-second timeouts, and multiple requests/agents can compound delays. Native `-i` and finite lease deadlines do not themselves enforce AC-only behavior.

**Reproduced:** create one active fake assertion, hold an observation, change the fake power source to battery, and request a tick. After **2,301 ms of real elapsed time**, the assertion is still active and the power-read count is unchanged (3). Releasing the held observation allows removal. This proves the scheduling dependency, not physical unplug latency.

**Design consequence:** future evidence or metadata work directly delays safety reconciliation. A temporarily slow Herdr service can leave protection active on battery well beyond the intended polling cadence.

**Recommendation:** give power eligibility/removal a bounded cadence independent of Herdr reads and token publication, while maintaining one assertion owner and preventing stale work from reacquiring after newer battery evidence. A bounded refresh budget with explicit stale-power handling is an alternative; checking only at refresh start still leaves the next blocking interval.

**Decision:** require bounded safety scheduling, or explicitly accept and document the weaker AC-response contract. Test with held ports; no native assertion is necessary for the regression.

### R4 — “Set from now” can extend protection for an old remembered run instead of a verified current target

**What this could look like with the plugin installed:** you open an agent's controls while it is working and choose a longer duration. Before you submit, the agent finishes—or its current state can no longer be checked because Herdr reads fail. The plugin is supposed to check that your action still applies to the captured agent/run. Instead, it can accept the duration against its old remembered state and replace that run's deadline. A connection error may still be shown; the concern is that the operation is accepted despite the failed recheck, not that the UI necessarily looks error-free.

**The stakes:** your Mac can be kept awake for the new, longer duration even though the run you meant to protect has ended. You intended a targeted action, but the plugin cannot establish that the target is still current. The reproduction demonstrates an old run being extended; it does not demonstrate protection transferring to a replacement agent.

**What should happen:** ask you to retry when the plugin cannot verify the target's identity. This must not remove a useful existing feature: if the agent's identity is verified but its progress/activity is unclear, you should still be able to manually caffeinate it. “I can't tell whether this agent is busy” and “I can't verify which agent/run this action now refers to” are different situations.

**Fix before merge, narrowly scoped.** References: `herdr/caffeinate/src/monitor.ts:174–183,202–213`; `src/model.ts:99–108`; `src/herdr.ts:225–239`; `docs/design.md:127,145`.

**Important counterargument:** the design expressly permits manual caffeination of uncertain ongoing work. Activity uncertainty alone is **not** a reason to forbid manual protection. For example, a verified occupant followed by an `agent.explain` failure can still be a valid manual target.

**Observed defect:** `command()` awaits a refresh that can swallow host/list failures before current identity is established. It then validates the guard only against unchanged cached state and applies the command.

**Reproduced:** capture an active run's duration guard, change the simulated actual agent to idle, make listing fail, and submit a longer duration. The command succeeds (`rejected:false`) and changes its deadline from `1800028800000` to `1800072010000`. This demonstrates acceptance after failed revalidation, not actual transfer to a replacement occupant.

**Recommendation:** distinguish successful host/target identity revalidation from uncertain activity. Reject grants/extensions/arming when identity revalidation fails; retain the approved manual behavior when identity is established but activity is uncertain. Preserve existing leases. Blanket rejection of all uncertain observations would remove approved functionality. Whether release/cancel remains available is a separate, narrow policy choice.

**Decision recorded:** Zack explicitly requested this correction in Crit round 2: “great catch, really tough timing. definitely fix.” The approved direction retains manual protection for a verified agent with uncertain activity, but rejects grants against an unverified cached identity. A targeted independent follow-up considered that distinction and retained the narrowed finding. R4 repair is authorized for the subsequent repair phase; no implementation has been changed during report review.

### R5 — A developer cannot install the package from a fresh checkout

**What this looks like for a developer:** you clone the repository, use the supported Node 24 release installed on your machine, and run the documented frozen dependency installation. It stops with an incompatible-Node error. In our reproduction, the actual Node was 24.16.0, but the error said “Got: 24.0.0.” The normal check command also stops when it tries to verify/install dependencies.

**The stakes:** a new contributor or clean build environment cannot reproduce the package's advertised setup and verification process. An existing prepared plugin payload can still run—the relocated payload did run on Node 24.16.0—so this is not evidence that every currently installed plugin fails to launch. However, the package's declared minimum and its chosen build tools disagree, and clean development/release preparation is blocked.

**Why the confusing version appears:** pnpm checks whether the tools support the lowest Node version the project promises, not just the newer Node executing the command. The project promises 24.0.0, while some pinned build tools require at least 24.11.0. The strict check is exposing a real compatibility mismatch.

**Decision already made:** Zack is comfortable raising the common floor. Users and developers below the newly selected minimum would need to upgrade Node; the exact minimum still needs checking against the complete dependency chain. No implementation has been changed yet.

**Fix before merge; higher-floor policy approved, exact minimum pending verification.** References: `herdr/caffeinate/package.json:41,47,52`; `pnpm-workspace.yaml:4`; `pnpm-lock.yaml:820,863`.

**Observed:** with actual Node **24.16.0** and pnpm **11.26.0**, both a pristine export and a copy containing existing dependencies fail frozen installation:

```text
Your Node version is incompatible with "tsdown@0.23.0(typescript@7.0.2)".
Expected version: ^22.18.0 || ^24.11.0 || >=26.0.0
Got: 24.0.0
```

**Established cause:** pinned pnpm derives its dependency-check `nodeVersion` using `semver.minVersion(devEngines.runtime.version)`, which yields 24.0.0. Strict engine checks then reject the pinned tools; tsdown and rolldown-plugin-dts require at least 24.11.0 on Node 24. `onFail: "error"` does not disable this derivation. Installed pnpm source was inspected at `dist/pnpm.mjs:171790–171791,172263–172279,108226–108274`. This explains the failure without assuming copied dependencies or inherited configuration; pristine failure rules out relocation of dependencies as a necessary cause.

`pnpm check` also fails when its dependency-status check invokes installation. The direct TAP spike-build failure has the same cause, not a demonstrated TUI bundle defect. Prior author-reported frozen-install success does not establish fresh-install support; its discrepancy remains unexplained.

**Alternatives:**

1. Preserve the approved common 24.0.0 minimum and select exact, policy-eligible tool versions whose full dependency chain supports it. Reverify build, bundle inventory and notices.
2. Explicitly raise the **common developer and runtime minimum** to at least 24.11.0 after checking the complete dependency chain. Update metadata, preflight, prepared payload, documentation and boundary tests together. This excludes earlier Node 24 consumers; their existence is unknown.

Do not force installation, disable strict engines, override the checked version to mask the contract, provision Node, or silently introduce different development/runtime floors.

**Decision recorded:** Zack approved the higher-common-floor direction in Crit round 1: “Totally fine to raise the floor.” Option 1 is retained above only as the alternative considered, not the selected direction. Check the full dependency chain before choosing the exact minimum, then require a pristine frozen install, normal checks and actual minimum/current Node execution; simulated version boundaries are insufficient. This records the compatibility decision, not permission to begin repairs during report review.

### R6 — A developer can get a false “source file is not typechecked” failure

**What this looks like for a developer:** you run the tests from a checkout reached through a macOS path alias, such as `/tmp`. A coverage test says a source file is not being checked by TypeScript, even though the compiler is checking it. Running the same test through the canonical `/private/tmp` path succeeds.

**The stakes:** you lose time investigating a nonexistent gap in typechecking, or a clean verification job fails only because of the path used to access the checkout. This does not establish any failure in the installed plugin. We verified that the supposedly different paths identify the very same filesystem file.

**Why does checkout location matter?** It does **not** change what TypeScript checks in this reproduction. Our extra coverage test asks the compiler for its list of checked files, then compares those absolute path strings with its own expected list. On macOS, `/tmp` is an alias for `/private/tmp`. The compiler can preserve the shell's `/tmp` spelling while Node resolves the test file's location to `/private/tmp`. An exact text comparison says the file is missing even though both names refer to the same file.

**When would a developer encounter it?** We encountered it by exporting this review checkout under `/tmp` and running the checks there. Another checkout reached through a symlink could produce the same kind of mismatch; that broader case was not separately tested. A normal `/Users/...` checkout without a path alias need not encounter it. The problem is our extra test comparing names, not TypeScript being sensitive to which directory contains the project.

**What should happen:** test file identity consistently rather than treating two names for one file as different files. Genuinely missing coverage must still fail.

**Optional improvement.** References: `herdr/caffeinate/test/quality-canaries.test.ts:8,23–38`; `tsconfig.json:14–23`.

The direct suite reports `Unchecked file: src/assertions.ts` under a `/tmp` verification path. The compiler lists `/tmp/.../src/assertions.ts`, while the expected import-derived path is `/private/tmp/.../src/assertions.ts`. A focused probe confirms **the same filesystem device/inode**, unequal strings, and compiler exit zero. With canonical `PWD`, the paths match and both quality tests pass.

This is a reproduced test-portability false positive, **not** evidence that assertions.ts escaped typechecking. It can make valid macOS checkouts accessed through symlinks fail the gate. Canonicalize listed/expected file identities and generated-output exclusion roots consistently; do not weaken coverage assertions or hardcode the `/private/tmp` spelling.

**Decision:** fix the portability issue now or defer with canonical-path verification documented. No runtime defect was established.

### R7 — The “clean installed payload” test can depend on hidden developer settings

**What this could look like for a developer:** the relocated-payload test passes on one machine but fails on another because one developer has Node startup options, a preload script, or a different executable search path configured. Those settings are inherited by the supposedly clean test. A preload could also influence a passing result, making it weaker evidence that a normal consumer needs only the shipped payload and documented prerequisites.

**The stakes:** maintainers could mistake an environment-dependent result for a portable install check, or spend time debugging a failure unrelated to the payload. We have not shown that any passing run was contaminated, and this is not a demonstrated installed-plugin defect.

**Would mise address this?** Yes for an important part: a pinned mise toolchain can make contributors and CI select the same Node and other tool versions. That is toolchain reproducibility. R7 is the narrower, separate question of which ambient settings the child process inherits. Merely selecting Node through mise does not establish that `NODE_OPTIONS`, loaders, or unrelated executable paths have been excluded; this test explicitly copies its parent environment. In fact, it already selects an absolute Node binary and puts that binary first in a private PATH directory.

The installed mise CLI also advertises `mise exec --deny-env` and `--allow-env`, so mise can participate in environment isolation **if those controls are deliberately used**, rather than relying on version pinning alone. Its help says `--deny-env` still passes through a small set including PATH and HOME. We inspected the help; we have not run or validated a mise-based test setup. The report does not claim that mise is incapable of isolation.

**What about Docker?** A Linux container could be useful for a clean toolchain/build or platform-neutral bundle check. It cannot, by itself, establish that the actual macOS plugin installation works: the real launcher requires macOS, Herdr is part of the consumer contract, and native sleep assertions use macOS facilities. Bypassing the platform check in Docker would test a different contract. A clean macOS runner or VM is more representative for installation testing; physical battery/display acceptance would still be separate. Docker is an option for later infrastructure work, not required to address this small finding.

**What should happen:** use a deliberately controlled test environment—whether created by the test itself or a verified mise/CI invocation—containing the selected Node and required Herdr executable, rather than assuming toolchain pinning also removes arbitrary developer startup settings.

**Optional improvement.** Reference: `herdr/caffeinate/test/runtime-compatibility.test.mjs:24`.

The test spreads `process.env` and appends the caller's entire `PATH`; the version probe also inherits environment. A preload/loader through `NODE_OPTIONS` could participate in a supposedly isolated payload run, or unrelated settings could cause failures. This is a static test-isolation concern; no contamination of the reported passing run was demonstrated.

Use an explicit minimal environment with the selected preinstalled Node and required Herdr executable. This increases setup slightly but makes evidence/failures more local. The separate Herdr sandbox already uses a more explicit environment.

**Decision:** accept or defer; this alone need not block merge. Zack is open to Docker-based installation testing and asked how this relates to future mise infrastructure. That is recorded as openness to an infrastructure option, not a decision to implement Docker/mise configuration as part of this review.
